EnMS 不是只把能耗資料說成人話，而是開始具備可驗證的預警、異常、告警能力。

目前 EnMS 已接入 DenchClaw 的同一套 planner / context / learning / review contract， 並補上第一版 Demand Forecast Engine、Anomaly Detection Engine、Alert Governance Engine。 這些模組屬於統計 + 規則式 analytics path，不是自研 foundation model。

目前 EnMS 能做什麼

Demand Forecast

以歷史 summary-layer 需量資料、同時段基線、最近趨勢、契約容量與可用營運特徵做需量預警。

Anomaly Detection

先在 summary layer 建立需量 / 功因基線，再用 raw layer 驗證 THD、quality、connected、三相異常。

Alert Governance

把 forecast 與 anomaly 整理成 prewarning / alert，並附 recommended owner 與 escalation window。

資料主線

資料層 主要來源 角色
摘要層 DeviceDataSummaryView 需量、KPI、趨勢、benchmarking、預警的第一優先資料層。
原始層 mqtt_raw_data 異常偵測、電力品質、連線掉點、根因 drill-down。
主資料層 ElectricityMeter、PowerAccounts、sites、site_gateways、ComCompany 補設備別名、契約容量、場域、gateway、公司層語意。
EnMS 的第一原則是 summary-first、raw-validation、join semantics before answer。 也就是先用摘要層看趨勢，再用 raw 驗證異常，最後一定補上設備 / 場域 / 契約語意。

缺資料治理已經補進主聊天

Bootstrap

主聊天命中 EnMS 時，會先補一段 live DB bootstrap，確認 sites、PowerAccounts、DemandAlertHistory 等資料可用性。

Response Contract

若契約容量或告警歷史缺資料，回答必須直接點名哪張表 0 rows，並退回仍可驗證的 summary-layer 分析。

例如目前若 PowerAccounts 或 DemandAlertHistory 沒資料，系統不應再只回「因資料限制」， 而是要清楚說出缺口，並改做最大需量、summary 趨勢或 raw signal 檢查。

三個分析模組怎麼做

1. Forecast Logic
  • 同時段歷史基線
  • 最近 8 筆 summary 趨勢
  • 可用的溫度 / business load / production load 特徵
  • 契約容量比對後輸出 risk level 與 prewarnings
2. Anomaly Logic
  • 需量 spike 基線比對
  • 低功因與契約容量壓力
  • connected / quality 掉點
  • THD、phase imbalance 等電力品質異常
3. Governance Logic
  • forecast output + anomaly output 合併
  • 切成 prewarning / alert
  • 建議 owner：energy_manager / facility_ops / electrical_maintenance
  • 避免把所有訊號都扁平成同一級警報
