這份文件不是概念簡介，而是面向後續產品化與技術投資判斷的實作基準。 基於 2026 年 6 月 3 日 實際檢視的 EnMS 頁面 http://118.168.188.27:5174/#/AIAssistant，本文件把目前 mockup 的 6 個分頁， 對照到 EnClaw 現有 runtime、已落地能力、資料缺口、演算法缺口，以及未來版本演進步驟。

目前頁面狀態

AIAssistant 頁目前是 iframe 載入靜態 mockup，不是已接上真實 AI runtime 的正式功能頁。

目前主線

自然語言查詢、需量預警、異常偵測、Alert 治理，已可直接對應到現有 EnClaw runtime 與分析模組。

文件口徑

本文件以「現有主線、資料缺口、演算法缺口、版本演進」四個角度整理，可直接作為後續拆分工作包與對外說明邊界的依據。

固定設計前提

資料分層

先固定使用三層資料：原始時序層 mqtt_raw_data、摘要分析層 DeviceDataSummaryView、主資料層 ElectricityMeter、 PowerAccounts、sites、site_gateways、 ComCompany。

缺資料治理

若 PowerAccounts、DemandAlertHistory 或主資料不足， 必須明講缺哪張表、還能回答什麼，不允許用模型硬猜契約容量、警報歷史或 ROI。

圖表輸出契約

正式圖表可走可執行 SQL；若只是 renderer 驗證或已經先拿到聚合結果，可用 VALUES 或 inline rows/data，避免讓壞 payload 直接進前端。

回答流程

一律走 planner → bootstrap → context pack → analytics module → answer / chart → review， 不直接把資料問題丟給模型即興回答。

控制延伸

若既有 EnMS 已打通 MQTT、PLC、Modbus、BACnet、OPC UA 或其他 protocol adapter， 後續可進 human-approved semi-closed-loop；但目前不把全面自動控制當現況宣稱。

文案邊界

沒有實作的特定模型名不要先寫進正式功能說明。先寫能力與方法，再隨實作版本補上具體演算法名稱。

未來版本演進步驟

如果要把整個 AIAssistant 頁面推進到正式產品，版本演進不應按 UI 分頁平行開發，而應依 runtime 完整度、資料依賴與分析閉環成熟度分階段推進。

Version 1. 建立 AI-04 自然語言查詢主線

優先將 EnMS 端 mockup drawer 換成真實 chat runtime。這一條線最接近現有 EnClaw 主線，也最能快速驗證 query、chart、缺資料治理與報表跳轉整合。

Version 2. 接 AI-01 需量預警與 AI-09 Alert 治理

這兩塊直接連到 summary layer、contract capacity 與 alert policy，是最容易形成營運價值與管理端感知差異的能力建設。

Version 3. 補 AI-03 異常偵測與根因分析

待 raw data 品質與主資料語意穩定後，再把 power quality、THD、connected、phase imbalance 與 root cause path 補齊。

Version 4. 建立 AI-10 能效分析第一版 recommendation path

先讓系統穩定輸出可審核的節能建議與改善方向，再進入 ROI 與 what-if simulation。

Version 5. 強化 AI-05 多場域 Benchmarking 與 AI-10 ROI / what-if

這兩塊對資料正規化、主資料完整度與專用演算法要求最高，應放在前述主線穩定後推進。

對外表述邊界

不應直接視為現況
  • LSTM 已正式上線。
  • Isolation Forest 已正式上線。
  • k-means 已用於多場域分群。
  • 已全面自動化 closed-loop control。
  • 已是 field-proven 的工業級 forecasting platform。
目前較準的說法
  • 已具備第一版可驗證的需量預警、異常偵測、Alert 治理與自然語言查詢 runtime。
  • 多場域 Benchmarking 與 ROI / what-if 模擬已有明確技術路徑，但仍需補資料模型與專用演算法。
  • 控制可延伸到 human-approved 或 policy-governed 的半自動閉環控制，但不把它包裝成現況。
