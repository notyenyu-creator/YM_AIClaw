EnClaw / 技術架構深度介紹 / 中文技術版

核心價值在於可持續運作的企業 AI 執行框架。

EnClaw 的技術主體由 Gateway 執行層、問題判斷與 Context 組裝、分析引擎、 Karpathy-style AI Wiki 知識層 與 Review 流程構成。核心價值不在單一模型品牌， 而在讓 AI 能以 可審核、可追溯、可擴充 的方式進入真實業務流程。

主線架構

Cloud API 模型、OpenClaw Gateway、Hermes-style Planner、AI Wiki 知識層與 Review 流程。

核心價值

差異化能力集中在資料判斷、分析引擎與知識治理，而不是單一模型供應商。

對外定位

目前定位為 AI decision layer，並保留往半自動閉環控制與更高自動化延伸的技術路徑。

內容原則

本頁僅陳述已落地能力、已驗證的交付邊界，以及具明確技術主線的後續演進方向；未驗證方向不視為現況能力。

四項核心技術價值

資料主權 / Source-of-Truth Routing

系統先判定資料來源、可信表與合理關聯，再開始回答，避免在資料不完整時產生錯誤推論。

治理型執行框架 / Governed Runtime

AI 回答會經過 session、planner、context、review 與 promotion，整個流程可被追蹤、審核與回放。

可解釋分析引擎 / Explainable Analytics

Forecast、anomaly 與 alert 先由程式化分析模組建立基線與訊號，再交由 AI 組織說明與建議。

可嵌入式 AI 層 / Deployable AI Layer

EnClaw 可疊加在既有 EnMS 之上，不必先重做主平台；長期資產在執行框架，而不是單一模型。

架構設計原則與非功能要求

高階技術架構文件不只描述功能流程，也必須明確交代安全性、可觀測性、可靠性、效能與可擴充性。以下原則對應 EnClaw 目前的實作方向。

維度 設計原則 在 EnClaw 的落點
Security / Governance 模型呼叫、資料查詢、知識寫回與控制延伸，都需要有清楚的權限與治理邊界。 以 session、review、promotion、缺資料治理與 human-approved control path 作為治理邊界，不把高風險動作直接自動化。
Observability 每一段流程都應可追蹤、可檢查、可回放，避免 AI 成為不可觀測的黑盒。 透過 planner artifacts、bootstrap snapshot、report runtime、review queue 與 wiki promotion 保留完整中間產物。
Reliability 資料不足、模型供應異常、圖表查詢失敗時，系統應能降級而非直接失效。 缺資料時明確回覆資料缺口；圖表可在可執行 SQL、VALUES-based SQL 與 inline rows/data 間降級切換；控制延伸目前維持 human-approved 邊界。
Performance / Cost 昂貴的模型推理不應取代可程式化的資料判斷與分析邏輯。 由 summary layer、forecast engine、anomaly engine 與 alert governance 先行產生訊號，再交由模型組織說明與建議。
Extensibility 模型、資料源、控制介面與知識規則都應能逐步替換或擴充，而不必重做整體架構。 模型層可替換；若既有 EnMS / 現場 gateway 已打通對應 protocol 與 adapter，EnClaw 可沿用該接入條件持續擴充。

資料管線：從接入到可分析資料

本段聚焦於 EnMS 資料如何自現場接入、完成分層與語意補齊，最終形成可供 AI 分析與治理使用的資料基礎。

1. 現場資料接入

既有 EnMS 透過 MQTT、PLC 或其他已打通的 protocol adapter 接收監測裝置資料，形成原始訊息與時序資料來源。

2. 原始資料落地與標準化

原始訊息會進入 mqtt_raw_messages 與 mqtt_raw_data 等資料層，完成欄位展平、時間序列標準化與設備訊號整理。

3. 摘要層建立分析基線

系統透過 DeviceDataSummaryView 建立 15 分鐘摘要層，作為需量預警、趨勢分析、KPI 比較與圖表輸出的主要基礎。

4. 主資料補齊語意

再將摘要層與原始層對回 ElectricityMeter、PowerAccounts、sites、site_gateways、ComCompany 等主資料，補齊設備、場域、契約與公司語意。

5. 形成可分析資料基礎

到這一步，EnMS 已具備原始時序層、摘要分析層與主資料層，可供後續預警、告警、趨勢分析與圖表輸出使用。

當使用者詢問預警 / 告警時的完整流程

以下流程描述的是一個典型情境：當資料已進入 EnMS，而使用者詢問「這個場域有沒有需量預警」或「目前有哪些告警需要處理」時，系統如何從資料表 / View 一路走到可執行的輸出。

分析資料分層

原始時序層：mqtt_raw_data、mqtt_raw_messages；摘要分析層：DeviceDataSummaryView；主資料與治理層：ElectricityMeter、PowerAccounts、sites、site_gateways、ComCompany、DemandAlertHistory。

問題判斷

Planner 判定這是 demand_forecast 或 alert_governance 類型問題。

資料檢查

Bootstrap 檢查表、欄位、join、契約容量與告警歷史是否可用。

Context 組裝

將主資料語意、分析規則、圖表限制與回覆邊界組裝進 context。

↓
Forecast Engine

以摘要層建立 baseline、recent trend 與 contract-capacity risk，生成 projected peak 與風險等級。

Anomaly / Alert Engine

整合 anomaly 訊號、設備狀態與既有規則，產生 prewarning / alert、owner 與 escalation window。

輸出層

回答可帶摘要、圖表、風險分級與建議動作；必要時再進入 review 與知識沉澱。

1. 使用者提出預警或告警問題

例如詢問「大溪廠未來 24 小時是否有超約風險」或「目前有哪些告警需要優先處理」。

2. Chat Route 建立 session 與執行上下文

訊息先進入 /api/chat，並與當前 session、planner artifacts 與 review 狀態綁定。

3. Planner 判定問題屬於預警或告警治理

apps/web/lib/enms-context-builder.ts 會辨識 intent、confidence、是否允許圖表，以及是否需要進一步 review。

4. Bootstrap 檢查資料可用性

apps/web/lib/domain-bootstrap.ts 先確認 PowerAccounts、DemandAlertHistory、DeviceDataSummaryView 等是否可用，避免在資料缺口下直接下結論。

5. Context Pack 組裝分析規則

apps/web/lib/enms-context-pack.ts 會決定這次優先使用摘要層、原始層或主資料層，並附上 summary-first / raw-validation / join semantics 等執行提示。

6. 分析引擎產生中間判斷

enms-demand-forecast-engine.ts 生成預警訊號；enms-alert-governance-engine.ts 匯整 anomaly、owner、priority 與 escalation window，形成可執行的 alert view。

7. 生成回覆、圖表與建議動作

若資料完整，系統輸出風險分級、趨勢圖、處置優先順序與建議動作；若資料不足，則明確說明缺口與可回答範圍。

8. 必要時進入 Review 與知識沉澱

若本次結論具代表性，後續可進入 learning draft、review、promotion 與 AI Wiki，形成可重複使用的知識資產。

失效邊界與降級策略

高階技術架構文件通常會說明系統在資料缺口、依賴異常或輸出失敗時如何維持可用。EnClaw 採用可預期、可追溯的降級策略，而非隱藏失效狀態。

情境 風險 系統處理方式
契約容量或告警歷史缺失 無法直接判斷超約風險或告警歷史。 由 bootstrap 明確標示缺口，回覆目前仍可回答的需量、趨勢或異常資訊，不直接猜測契約容量。
摘要層不足 預警與 KPI 分析缺乏穩定基線。 降低 forecast 信心，必要時退回 raw layer 檢查與保守說明，不輸出高置信度預測結論。
圖表查詢失敗 圖表無法渲染或 SQL 查詢失敗。 保留文字分析結果，並以 query error 或 fallback data 明確呈現，不以空白圖表掩蓋錯誤狀態。
模型供應異常 自然語言整理與生成受阻。 Gateway 與 session runtime 維持執行邊界；核心資料判斷與中間產物仍可保留，避免整個工作流失去可追蹤性。
控制條件尚未完備 控制權限、回滾機制、protocol adapter 或現場治理條件不足時，不適合直接進入自動控制。 系統先維持在分析、建議與 review 模式；當控制介面、權限邊界與安全條件完備後，可隨版本迭代逐步提升到半自動，甚至更高程度的閉環控制。

現場接入能力與控制延伸

現有接入能力

既有 EnMS 目前已透過 MQTT 與 PLC 接收監測裝置資料，這也是摘要層、原始層與告警分析的基礎來源。現場若有對應 gateway、driver 或 protocol adapter，通常也可接 Modbus、BACnet、OPC UA、MQTT、REST API 等介面。

本節描述的是既有 EnMS 的現場接入前提，而非 EnClaw 單獨提供的 protocol stack。能否接入，視現場裝置、通訊協定、gateway 與既有 EnMS 接入方式的整合完成度而定。
技術定位

EnClaw 的技術定位不是直接取代 PLC / BMS / SCADA 的控制邏輯，而是建在 EnMS 之上的 AI decision layer。其角色是負責分析、判讀、預警、告警治理與建議，再由人員或既有控制系統執行控制決策。

環節 1

AI 先分析
讀取 EnMS summary / raw / master data，判斷需量風險、設備異常或節能機會。

環節 2

AI 產生控制建議
例如建議降載、切換排程、限制某段時間啟動高耗能設備。

環節 3

人工確認
由 energy manager、facility ops 或 electrical maintenance 確認是否執行，避免直接自動下錯指令。

環節 4

再送控制命令

通用執行路徑

使用者從 EnMS chat 入口提出問題

例如詢問最大需量、契約容量風險、功因異常、THD、告警分級或節能建議。

Chat route 建立 session runtime

訊息先進到 /api/chat，並與當前 web session、planner artifacts、review 狀態綁在一起。

Planner 判斷 intent 與 domain

系統不直接將問題交給模型，而是先判斷其所屬 EnMS intent，並決定是否允許圖表、最多幾張圖，以及是否存在風險訊號。

Bootstrap 補齊 schema 與缺資料摘要

runtime 會先查可用表、主資料關聯、關鍵欄位與資料缺口，並明確標示目前能回答到哪一層。

Context pack 注入 domain 規則

例如 EnMS 會優先採用 summary-first、raw-validation 與 join semantics before answer，確保回答不脫離主資料語意。

分析模組先生成中間判斷

需量預警、異常偵測、告警治理等中間結果不由模型即興推測，而是由獨立 engine 先建立基線與訊號。

圖表 runtime 決定採用可執行 SQL、VALUES 常量或 inline rows/data

正式分析可走可執行 SQL；若只是 renderer 測試或要把已查證結果快速視覺化，也可用 VALUES 常量或 inline rows/data，兩者共用同一個前端渲染器。

結論可進入 review / promotion

若本次結論具有可重用價值，後續可進入 learning draft 與 review 流程，沉澱為 durable knowledge。

關鍵技術選型與作用

技術 / 模組 作用 核心價值
Next.js / React / TypeScript Web runtime、chat UI、review UI、debug page、session surface。 讓 AI 行為不再停留於抽象 API，而是成為可展示、可驗證、可審核與可操作的產品層。
OpenClaw-style Gateway Runtime 承接模型呼叫、transport、session、active runs、planner artifacts persist。 把 LLM 從單次呼叫變成可治理、可持續追蹤的執行 runtime。
Domain Context Builder / Pack 負責 intent、matched keywords、chart guardrails、references、execution hints。 把 prompt engineering 提升成程式化的 routing and context orchestration。
Domain Bootstrap 整理 schema、availability、joins、gaps 與 remaining answerable scope。 避免 AI 在 enterprise data 不完整時硬裝懂，提升可信度。
Report Runtime 將 report-json 轉成圖表，並支援可執行 SQL、VALUES-based SQL 與 inline rows/data 多種輸出模式。 讓正式分析圖表與前端渲染驗證共用一套前端能力，同時保留失敗時的可降級路徑。
Karpathy-style AI Wiki / Review Flow draft、writeback、promotion、review workspace 與 wiki 知識沉澱；實作上是以 wiki / schema / review-promotion 流程承接，而不是單獨一個獨立 skill package。 讓 AI 不只會答，而是能持續把知識變成可維護、可引用、可 promotion 的長期資產。

運行指標與持續驗證

參考高階架構文件的慣例，技術設計不應停在元件與流程，還需要定義系統上線後應持續追蹤的指標。以下指標構成建議的運行觀測框架，並可隨版本演進納入儀表板與運維監控。

指標類別 建議觀察指標 代表意義
資料層 資料新鮮度、summary refresh 狀態、主資料完整度、缺口比例 判斷預警、告警與分析是否建立在穩定資料基礎之上。
AI 路由層 intent 命中率、domain routing 正確率、chart guardrail 命中情況 判斷 planner / context 是否能把問題送進正確分析路徑。
分析層 預警命中率、告警誤報率、異常根因覆蓋率、趨勢分析穩定度 反映 forecast、anomaly、alert governance 的實用性與可靠度。
輸出層 圖表成功率、文字回覆完整度、缺資料回覆準確性 確保使用者實際看到的是穩定、可用且可執行的輸出。
治理層 review 通過率、promotion 比例、知識重用率 衡量 AI 是否真正把案例沉澱成可持續使用的知識資產。

目前定位與迭代方向

本節明確界定目前已具備的能力、現階段的交付邊界，以及後續可持續擴展的方向。

目前已具備
  • 核心技術已落在 runtime、bootstrap、analytics 與 reviewable knowledge loop。
  • 主力模型路徑可替換；EnClaw 的長期資產在執行框架、資料治理與知識沉澱。
  • EnMS 已具備程式化的預警、異常偵測、告警治理、圖表分析與缺資料治理能力。
持續迭代方向
  • 控制層目前以 human-approved 或 policy-governed 半自動閉環控制為主，後續可隨現場控制條件逐步提升自動化程度。
  • forecast、anomaly、alert 已有第一版 explainable analytics，效果會隨資料累積與場域校準持續提升。
  • 分析精度與告警門檻會依歷史資料長度、主資料完整度與場域特性持續優化。
