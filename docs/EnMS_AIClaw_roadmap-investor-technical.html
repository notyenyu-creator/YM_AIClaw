階段設計原則

每 2 到 3 個月都要有可發佈版本：先讓系統答得對，再讓它治理得起來，接著讓它分析得更深並能穩定重播；最後才分開驗證 4A 本地模型替代與 4B 可控的輔助控制試點。

8 大核心模組

8 大核心模組

六個分頁不是六套散裝功能，而是共用同一套 EnClaw AI operating layer（AI 營運層）。

本節同時說明產品壁壘與 runtime（執行底盤）職責，作為後續擴展不同能力頁的共用基礎。
系統邊界

AIAssistant 是入口，EnClaw 是共用 AI 底盤，EnMS 提供資料與既有執行介面，GX10 只是可切換的推理來源，VFD control（VFD 控制）則是需要 guardrail（安全護欄）與人工核准的受控執行路徑。

展開完整 8 大核心模組說明
1. EnMS-specific Runtime 擴充

投資語言：把通用聊天 runtime 轉成可被 EnMS 正式承接的產品底盤，是後續每個能力頁共用的基礎資產。

技術語言：在 chat / session / active-run runtime 中補上 EnMS routing、bootstrap、review 入口、analytics path 與 chart 接線。

2. Context Builder

投資語言：讓同一個問句能穩定落到對的業務語境，是答對率與可擴充性的核心壁壘。

技術語言：負責 intent 判斷、domain routing、schema / relation / query step 組裝，避免模型直接即興拼 SQL。

3. Context Pack

投資語言：把場域規則、知識、操作經驗與資料結構變成可重複利用的資產，而不是只留在人腦裡。

技術語言：整合 rules、wiki、playbook、integration profile、live query steps 與 domain cheat sheet。

4. Review Flow

投資語言：把 AI 產出納入可審核、可修正、可升級流程，才能把試用價值轉成組織資產。

技術語言：承接 learning draft、auto-trigger、human review 與 promotion 邊界，避免錯誤知識直接寫回。

5. 資料治理

投資語言：讓系統在資料不完整時依然可信，是工業導入裡最常被低估、卻最決定成敗的能力。

技術語言：處理 schema availability、join semantics、gap governance、缺資料提示與風險邊界。

6. 分析模組整合

投資語言：EnClaw 不只會聊天，而是把 forecast、anomaly、alert 等分析模組收斂成正式產品能力。

技術語言：整合需量預警、異常偵測、告警治理等引擎，讓回答有規則與統計依據，不只靠模型語感。

7. 圖表輸出

投資語言：把回答與圖表保持一致，才能讓管理層快速採信，也方便 demo、內部驗收與日常使用。

技術語言：提供 chart runtime、report execute path、renderer 契約與 chart guardrail，確保輸出可穩定落地。

8. Wiki Writeback 整合

投資語言：把一次次現場對話、修正與決策沉澱成可擴張的 know-how，是可複製的長期價值來源。

技術語言：將高價值經驗寫回 wiki、playbook、operation template 與 promotion path，形成知識閉環。

差異化能力

Answer Stability Contract（回答一致性契約）

這一層不是取代 8 大核心模組，而是在中後期把它們固定成可重播、可驗證、可回歸的企業解題契約。

目標是在資料、規則與模型路由不變時，同一問題問 10 到 50 次，核心答案、依據、查詢路徑與結論邊界都保持一致。
產品差異化

通用 AI 助手通常只能看到最後答案；EnClaw 要讓企業能掌握 intent（意圖）、context pack（上下文包）、query contract（查詢契約）、source provenance（來源依據）、answer template（回答模板）與 review trace（審核軌跡）。

技術核心

每次回答都產生 contract id（契約編號）、資料快照、SQL / tool trace（工具追蹤）、引用依據、風險邊界與 consistency score（一致性分數），讓回答可以 replay（重播）、diff（差異比對）與 regression（回歸驗證）。

落地節奏

0-6 個月先求功能可用；7-9 個月建立契約 PoC 與題庫；10-12 個月把契約回歸納入本地模型切換與 v1.0 驗收。

Contract 不是公開模型思考鏈

這裡要固定的是產品可審計的解題路徑：用了哪個 intent、哪份資料、哪個 schema、哪條 SQL、哪個 playbook、哪些 fallback（退回策略）與哪些回答模板。模型內部隱藏推理不需要暴露，但企業端需要可驗證的 reasoning trace（解題軌跡）。

詳細技術設計請見 回答一致性契約實作說明。

VFD control-assist

VFD control-assist（變頻驅動輔助控制）試點

第一個代表試點先以空壓機 VFD 為主，因為它兼具高耗能、邏輯清楚與成效易量化的特性。第一階段先在 /AIAssistant 做 AI 建議驅動的控制模擬與半自動決策輔助，再逐步把 Domain SME（領域專家 / 現場資深操作人員）的 know-how（現場操作經驗）沉澱成可治理、可驗證的產品能力；同一套治理、知識、審核與控制橋接機制，後續具備延伸到冰水主機、冷卻水塔、泵浦、風機、照明、通風、儲能、充電設備與可卸載負載的能力，但不代表短期已完成跨設備驗證。

控制能力將依序經歷模擬建議、經驗收斂、審核後 user trigger（使用者觸發）、半自動決策輔助與受控試點，不直接跳入全面自動化，也不把短期目標鎖死在單一設備族群。
01

Demo 層

第一階段先在 /AIAssistant 上做可展示的控制模擬 Demo，讓 AI 能根據資料提出調頻建議，並模擬半自動決策輔助的執行畫面與審核流程。

02

資料層

先確保空壓機壓力、負載、耗能、時段與上下游條件可穩定取得，建立可追蹤的調頻依據。

03

經驗層

收集 Domain SME（領域專家）與現場資深操作人員在不同情境下的 VFD 調頻數值、可調區間與禁區，讓後續推薦更改的數值有現場知識基礎，避免模型即興判斷。

04

知識層

把經驗沉澱成 wiki、playbook、operation template 與 control guardrail（控制安全護欄），為跨場域複製建立基礎。

05

控制層

透過既有 PLC（可程式邏輯控制器）、protocol adapter（通訊協定轉接器）或 control API（控制介面），在使用者 trigger 後先進入半自動決策輔助，再依安全 gate（安全驗收門檻）評估是否擴大成更高自動化等級，形成可審核的控制路徑。

控制邊界

第一階段的重點是把 Demo 做到可展示、可回放、可審核；真正的控制值依據仍建立在 Domain SME（領域專家 / 現場資深操作人員）的經驗數值與 guardrail（安全護欄 / 控制邊界規則）上，而不是直接讓模型自由生成調頻命令。短期先以建議、模擬、審核與 user trigger 為主，中後期再依設備特性、安全條件與現場成熟度評估更高自動化等級；正式控制仍受人工核准、設備保護邏輯與現場安全限制約束。消防、生命安全與關鍵製程主設備，不列入短期全自動目標。

模型策略

模型策略

雲端主模型維持穩定交付，本地模型則以量化方式逐步評估替代比例。

本地模型替代將以答對率、SQL 正確率、穩定度、延遲與成本進行量化評估。
穩定主線

現況穩定主線仍以雲端主模型為主，優先確保 query、治理與 chart 回答品質穩定可驗收；目前主要配置仍以 gpt-4.1-mini 為核心。

替代路線

GX10 本地模型是平行的成本與自主化路線，會透過 fine-tune、prompt tuning 與 routing eval 逐步驗證可替代比例，不直接宣稱已完成主力替換。

切換能力

目標保留本地 / AI API 可切換能力，讓題庫、穩定度、延遲與成本可以持續 A/B 驗證。

驗證重點

控制類功能更依賴 playbook、guardrail 與 rule。模型負責分析與建議，不單獨承擔控制責任。

結論

本節整理對外溝通時應保留的核心訊息。
1. AIAssistant 是明確的產品規劃入口

六個分頁已有功能藍圖與資訊架構草案，後續會沿著 phase 逐步接上真實能力。

2. EnClaw 底盤已足以支撐分階段正式化

共用的 query、chart、governance、review 與 wiki 能力，已形成可重用底盤與內部驗證能力。

3. 六個分頁會接到同一套核心機制

不是六套各自為政的功能，而是同一套 EnClaw AI operating layer 的不同入口。

4. 12 個月 roadmap 有清楚 phase 與完成條件

從 query、治理、分析到 control extension，phase 順序清楚；下一步重點是把 gate 持續量化。

5. 後段可延伸到 user-trigger 的空壓機 VFD control-assist

空壓機 VFD 是第一個代表案例，但後段差異化不只在單一設備，而在把 Domain SME know-how 產品化、可治理化，並以 user-trigger pilot 驗證受控決策輔助路徑；待控制邊界、知識沉澱與現場驗收成熟後，才逐步延伸到其他高耗能、可排程、可調節、可卸載設備族群。

補充邊界

本頁聚焦可公開分享的產品規劃、技術路徑與驗收邊界；/AIAssistant 定位為產品入口，正式化節奏依序為 query、governance、analysis 與後段驗證。若需進一步查看內部設計細節，建議於 NDA 情境下搭配附錄來源與 GitHub 實作脈絡一起說明。
