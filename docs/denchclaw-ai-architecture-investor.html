DenchClaw / AI Operating Framework / 中文技術版

DenchClaw 不是聊天外殼，而是把企業資料變成可執行 AI 的工作底盤。

核心不是自研本地大模型，而是把 OpenClaw Gateway、Hermes-style orchestration、AI Wiki、Y-CRM / ERP / EnMS domain adapter 收斂成同一條可治理 runtime。現在已能做跨系統 routing、reviewable learning flow，並在 EnMS 上補上第一版需量預警、異常偵測、告警治理模組。

看核心技術短版 看 EnMS 專頁 看驗證題庫
一句話定位

企業 AI operating stack，不是單一 chatbot，也不是只做文件檢索的 RAG 頁。

模型策略

主力是 Dench Cloud Gateway API，可切換 Claude / GPT 類模型；本地優先指部署與治理，不等於本地 LLM 推理主線。

目前最有說服力的地方

三系統共用同一套 planner / context / learning / review contract，EnMS 另外已補上程式化 analytics engine。

核心價值

把 source-of-truth routing、domain analytics、AI Wiki 治理，做成可持續運行的產品層。

三系統同構

Y-CRM、ERP、EnMS 共用同一套 runtime contract，但保留各自 schema 與資料策略。

EnMS 能力

不是只會聊能耗，而是已能對 summary/raw data 做需量預警、異常偵測、告警分級。

技術壁壘

重點不在模型品牌，而在 join rule、review 邊界、知識沉澱與跨系統執行治理。

現在多了一層 Bootstrap / Data Gap 治理

這層是最近補上的關鍵，讓三個系統在進模型前先把 schema、join、資料可用性講清楚。

Before LLM

Schema Bootstrap

Y-CRM 先讀 workspace auto-schema；ERP / EnMS 先做 live DB introspection，再把表、欄位、join 摘要注入 prompt。

Availability

Data Gap Detection

若表不存在、0 rows、或關鍵欄位語意未就緒，runtime 會先標示缺口，而不是讓模型直接猜。

Response Contract

Explicit Missing-Data Reply

遇到資料不足時，回答必須分成「已確認 / 缺少資料 / 目前可回答 / 建議下一步」，不能只說資料限制。

Verification

Prompt Audit Pack

另附一頁驗證題庫，專門用來檢查 Y-CRM / ERP / EnMS 是否真的走進正確 runtime。

架構只看四層就夠

這頁先講短版，避免主頁過長。更細的技術細節拆到 companion pages。

Layer 1

Gateway

承接 chat 入口、session runtime、模型供應與工具橋接。

Layer 2

Planner / Context

先做 domain routing、source-of-truth 決策、risk guardrail，再把最小上下文送進模型。

Layer 3

Analytics / Skills

Y-CRM / ERP / EnMS 各自有 domain adapter；EnMS 另有 forecast / anomaly / alert 模組。

Layer 4

AI Wiki / Review

回答後不是結束，而是進入 draft → review → promotion 的知識沉澱流程。

跟市面常見做法的差異

不是把 AI 寫得很神，而是把定位講準。

常見做法 通常停在哪裡 DenchClaw 的差異
聊天型 AI 模型回答 + 對話紀錄 有 session metadata、planner/context、review workspace、wiki promotion。
RAG / 文件檢索 切 chunk 後檢索回答 可接真實 DB、做 domain routing、跨系統整合與後續治理。
單一 BI Copilot 只在單一 schema 查詢與畫圖 可以跨 Y-CRM / ERP / EnMS 組裝決策上下文。
能管聊天頁 把能耗數字口語化 EnMS 已補上 summary-first forecast、raw anomaly validation、alert governance。
