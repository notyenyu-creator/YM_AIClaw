DenchClaw / 核心技術短版

核心技術不是自研大模型，而是可治理的 AI 執行框架。

DenchClaw 的技術重點是把模型層、企業資料層、domain routing、reviewable learning loop， 收斂成同一條可持續擴充的 runtime。模型可以替換，但執行治理、資料語意、知識沉澱與跨系統 contract 才是核心資產。

目前系統架構圖

目前的產品主線不是單一聊天頁，而是一條從 session runtime、planner、bootstrap、analytics 到 reviewable knowledge loop 的可治理執行鏈。

1. Web / Session

Chat、workspace、review、debug 都由 Next.js / React runtime 承接。

2. OpenClaw Gateway

負責模型呼叫、stream transport、active runs 與 session metadata。

3. Hermes-style Core

planner、context pack、bootstrap、chart guardrails 與 domain routing 先行。

4. Analytics / Review

EnMS analytics、report runtime、draft → review → promotion 形成長期資產。

模型層

核心價值

模型可換，但 routing、governance、data contract 與 analytics runtime 會持續留在產品裡。

最值得講的五個核心

1. Gateway

以 OpenClaw Gateway 承接 chat 入口、session runtime、工具橋接、模型呼叫與 metadata 保存。

2. Planner / Context

在模型前先做 intent、domain routing、source-of-truth 判斷、risk guardrail、context pack 組裝。

3. Domain Adapter

Y-CRM、ERP、EnMS 不是同一份 prompt，而是各自的 builder、pack、skill、join rule 與操作策略。

4. Reviewable Learning

回答後進入 draft → review → promotion，不直接把模型輸出當正式知識或正式資料。

5. Model Strategy

主力是 Dench Cloud Gateway API，可切換 Claude / GPT 類模型；本地優先指部署與資料治理，不是本地 LLM 主線。

附加價值

EnMS 現在已補上需量預警、異常偵測、告警治理模組，代表不是只有聊天理解，也有數值化 analytics path。

6. Bootstrap / Gaps

主聊天在進模型前，會先做 schema bootstrap，並把缺資料來源明確標示進 prompt，避免模型硬猜欄位或契約語意。

7. Chart Runtime

圖表層同時支援 validated SQL 與 inline rows/data。這讓真實資料圖表與 demo 驗證圖表都能走同一套 renderer。

8. Parity Audit

PM / RD / QA / TPM 不是口號，而是直接落成 domain parity audit，檢查三個系統的 runtime surface 是否一致。

缺資料時怎麼處理

Bootstrap Snapshot

apps/web/lib/domain-bootstrap.ts 會在 Y-CRM / ERP / EnMS 被命中時，先補一段 schema、join、availability 摘要。

Missing-Data Contract

若資料不足，回答必須分成 已確認、缺少資料、目前可回答、建議下一步，而不是只說資料限制。

圖表 Runtime 不是前端小功能

Route

/api/workspace/reports/execute 現在會分流 Y-CRM、ERP、EnMS 的外部 PG 查詢，而不是只支援單一系統。

Dual Mode

每個 panel 現在可用兩種資料來源：sql 或 rows/data。前者用於 live chart，後者用於 demo 與靜態驗證。

Guardrail

若 chart 只是測試用途，runtime 會鼓勵模型直接給 inline rows/data；若是正式分析，則要求先有非空聚合資料再畫圖。

Error Clarity

若 SQL 或欄位名錯誤，前端現在應看到 query error，而不是空白圖或誤導性的 No data。

多 Agent 驗證層

PM

檢查功能面是否形成完整 user flow，而不是只完成單點 API。

RD

檢查 builder、context、writeback、promotion、review path 是否真正接線。

QA

檢查缺資料回覆、錯誤處理、圖表 renderer 與 debug page 是否可重現驗證。

TPM

檢查三個 domain 是否維持同一套 runtime contract，而不是各自長成三個互不相干的產品分支。

跟市面上常見說法最不同的地方

問題 DenchClaw 的答案
你們的核心是不是某個自研大模型？ 不是。核心是 runtime、domain adapter、analytics engine、reviewable knowledge ops。
為什麼不自己做本地模型？ 對現階段小團隊，模型層外包給穩定 API 更務實；真正價值在資料語意、工作流、治理與垂直 know-how。
你們跟聊天型 AI 有什麼差別？ 不是只有回答，而是先做 routing、再做 analysis、最後可進 review / promotion。
你們跟單一 BI Copilot 有什麼差別？ 可跨 Y-CRM / ERP / EnMS 做統一 contract，不是只對一套 schema 問答。
