EnMS x EnClaw / 回答一致性契約

把企業問答從「每次重新生成」升級成可重播、可驗證、可回歸的解題契約。

這份文件定義 EnClaw 的中後期差異化能力：同一個問題在相同資料、規則與模型路由條件下，問 10 到 50 次時，核心答案、查詢依據、圖表資料與結論邊界都要保持一致。

產品定位

這不是要求模型公開黑箱思考，而是讓產品掌握可審計的解題路徑。

一句話

模型可以是可替換元件；EnClaw 自己掌握 intent、context、data snapshot、query、evidence、template、review 與 replay。

EnMS × EnClaw 的整合定位

`EnClaw` 在這裡不是外掛式聊天工具，而是要整進 `EnMS` 的 AI operating layer（AI 運作層）。`/AIAssistant` 是 `EnMS` 內的產品入口，`EnClaw` 負責 intent、context、query、evidence、template、review 與 replay，`EnMS` 則提供資料來源、既有流程與執行介面。

通用 AI 的弱點

同一問題多問幾次，文字、判斷順序、引用資料與風險邊界可能漂移；使用者很難知道差異來自資料、模型，還是提示語。

EnClaw 的產品機會

把回答拆成固定契約：先定義問題類型，再鎖資料與查詢，再輸出可驗證答案。自然語句可以不同，但核心事實不可亂跳。

落地原則

早期先求功能可用；中期把高價值題庫納入 contract；後期把 contract regression 納入模型切換與 release gate。

邊界聲明

Answer Stability Contract 不等於公開完整 chain-of-thought。企業真正需要的是可查證的 reasoning trace：用了哪個 intent、哪份資料、哪條 SQL、哪些證據、哪些規則與哪些 fallback。

名詞定義

正式採用 Answer Stability Contract；Reasoning Contract 只作為輔助說法。

命名原則

這裡的 contract 是產品與系統承諾遵守的約定，不是模型自由生成的說明文字。

名詞 建議用法 定義 使用邊界
Contract 通用工程名詞 系統對輸入、流程、資料來源、輸出格式、錯誤處理與驗收條件的固定約定。 可類比 API contract、schema contract、data contract；重點是可驗證與可回歸。
Answer Stability Contract 正式推薦名詞 EnClaw 用來約束企業 AI 回答一致性、資料依據、查詢路徑、圖表輸出、fallback 行為與結論邊界的產品契約。 對外、對內都可使用；最能避免被誤解為公開模型內部思考。
Reasoning Contract 輔助說法 指可審計的解題路徑契約，例如 intent、context pack、query contract、evidence ledger、answer template 與 replay log。 不等於 chain-of-thought；文件中使用時要明確說明是產品可審計路徑，不是模型內部隱藏推理。
Answer Contract 單次回答實例 一次使用者問題產生的具體 contract instance，包含 contract id、資料快照、查詢、證據、圖表資料與回答模板。 適合用在 run log、review、debug 與 QA 報告中。
Contract Regression 測試與 release gate 每次更換模型、修改 prompt、更新 schema、調整 query builder 或改 playbook 時，用固定題庫重跑 contract，檢查答案是否穩定。 是模型切換與版本發布的必要 gate；不能只看單次回答看起來合理。
Reasoning Trace 稽核與 debug 名詞 企業可查證的解題紀錄，包含路由、資料、工具、查詢、證據、缺資料與模板選擇。 只保存產品可審計紀錄；不保存或展示模型完整 chain-of-thought。
後續文件統一寫法

正式文件優先寫 Answer Stability Contract。需要描述解題路徑時，可以寫「Reasoning Contract / 可審計解題路徑」，但必須補充它不是模型內部 chain-of-thought。

Contract 結構

每次回答都產生一份可重播的 Answer Contract。

設計重點

Contract 要固定可驗證欄位，不把穩定性寄託在模型自由發揮上。

欄位 用途 穩定性意義
contract_id 由 workspace、intent、normalized question、資料版本與 schema 版本產生。 辨識同題是否應該重用同一解題路徑。
intent_contract 固定問題類型、領域、允許工具、禁止跨系統回答規則。 避免 ERP 問題跑出 EnMS 回答，或 EnMS 查詢誤用 Y-CRM path。
context_pack_fingerprint 記錄 schema、wiki、playbook、資料時間窗與權限範圍。 回答改變時可以判斷是否因 context 改變。
security_scope 保存 tenant_id、actor_id、authz_policy_version、資料分類與可見範圍。 避免 replay 或 debug 時跨 tenant、跨 domain 或越權重跑資料。
query_contract 保存 SQL / tool call、參數、時間範圍、fallback 規則與資料來源優先序。 同題同資料應取得同一批 facts 與 chart data。
snapshot_manifest 保存 snapshot_ref、as_of、timezone、指標版本、結果 canonical hash 與 retention 規則。 讓 replay 不只靠 hash，而是能明確知道比較基準與資料時間點。
evidence_ledger 保存資料表、欄位、結果摘要、引用來源與缺資料說明。 答案不是模型說了算，而是 evidence ledger 說了算。
answer_template_id 固定回答段落順序、日期說法、單位格式、風險說明與下一步建議。 讓文字表達可以自然，但結構與關鍵內容穩定。
consistency_score 比較多次 run 的 facts、evidence、chart data、warning、recommendation。 把「感覺穩不穩」變成可量化 gate。
version_manifest 保存 source schema、query builder、prompt、model route、answer template、evaluator 版本。 讓回歸失敗時能定位到底是資料、查詢、模板還是模型版本造成差異。
replay_log 保存可重跑的輸入、資料快照 hash、模型路由、輸出摘要與 diff。 用於 QA regression、模型 A/B 與客戶爭議追查。

最小安全與版本邊界

正式上線時，每次 replay 都必須同時帶出 security_scope、snapshot_manifest 與 version_manifest。這樣才能區分「答案改變是資料改了、規則改了、模板改了，還是權限邊界不一樣」。

Runtime 流程

同一問題要先進 contract，再進模型，而不是每次都讓模型重新決定流程。

工程原則

能由程式固定的部分就固定，讓模型只處理需要語言理解、摘要與表達的部分。

1

Normalize

正規化問題、日期、場域、單位、同義詞與系統 domain。

2

Route

鎖定 EnMS / ERP / Y-CRM 等 domain 與 intent contract。

3

Pack

組 context pack，產生 schema、wiki、playbook 與資料 fingerprint。

4

Query

執行 DB-first / tool-first 查詢，保存 query contract 與 evidence ledger。

5

Render

使用固定 answer template 輸出文字、圖表與缺資料說明。

模型在這裡扮演什麼角色

模型負責語意理解輔助、摘要、語氣與建議草稿；決定資料來源、時間窗、schema、query、fallback 與驗收分數的主體應該是 EnClaw runtime。

一致性評分

同題 10 到 50 次，不要求逐字相同，但要求核心事實與依據一致。

建議 Gate

先從高價值 Top 30 題庫開始，跑 10 次；穩定後擴大到 50 次與跨模型 A/B。每次都要固定 snapshot_manifest.snapshot_ref、security_scope、prompt_version、answer_template_version 與 model_route_version。

100%

在固定 data snapshot、prompt 版本與 answer template 下，資料來源、時間窗、canonical result hash、chart data hash 必須一致。

>= 95%

核心 facts、排名、金額、kWh、警示分類與引用依據需高度一致；允許格式與四捨五入有極小差異。

>= 90%

建議文字、下一步說明與摘要可有語氣差異，但不能改變結論方向或風險邊界。

檢查項 比較方式 失敗時處理
Intent Stability 同題多次是否落在同一 domain、intent、allowed tools。 調整 router prompt、intent classifier、domain guardrail。
Data Stability 資料時間窗、source priority、SQL hash、canonical result hash 是否一致。 鎖定 query builder、時間解析與 fallback 規則。
Evidence Stability 引用資料表、欄位、playbook、wiki 條目是否一致。 調整 context pack ranking 與 source-of-truth 優先序。
Answer Stability 核心事實、排名、風險分類、建議方向是否一致。 固定 answer template，降低自由生成範圍。
Model Switch Stability gpt-4.1-mini 與 GX10 本地模型是否通過同一 contract regression；A/B 時固定 route、prompt、template 與資料快照，只允許 model_backend 變動。 保留 API fallback，將本地模型限制在已通過 intent。
Authorization Stability 同一題在相同 tenant、actor、authz policy 下，是否維持相同可見資料範圍。 若 scope 不一致，視為高風險失敗，必須先修正權限邊界再重跑。
Replay Protocol 與 Golden Dataset

每次一致性驗收都要固定 snapshot_manifest.snapshot_ref、security_scope、prompt_version、model_route_version、answer_template_version 與題庫清單。若做跨模型 A/B，比較時唯一允許變動的是 model_backend。正式題庫至少分成正常案例、缺資料案例、空時間窗、跨場域比較、晚到資料、告警分類、越權拒答與控制邊界案例，避免只用 happy path 驗證。

導入 Roadmap

排在中後期：先求有，再求穩，再求可替代。

節奏判斷

一致性契約要建立在 query / governance 已經能運作的基礎上，太早做會變成空契約。

0-6 個月：埋 trace，固定最小契約

先讓自然語言查詢、圖表、缺資料說明、alert governance 跑起來；同時固定 contract schema v0、query hash、evidence ledger、snapshot manifest 與 version manifest，為後續 regression 做資料準備。

7-9 個月：Answer Contract PoC

挑選 Top 30 題庫與 3 條高價值分析主線，建立 contract schema、answer template、replay runner 與 consistency score；其中 Top 30 與 1 條分析主線列為必達，其餘 2 條列為 stretch。

10-12 個月：納入模型切換與 release gate

將 contract regression 用在 gpt-4.1-mini / GX10 本地模型 A/B，依 `shadow -> canary -> partial -> default` 逐步驗證，只有通過 gate 的 intent 才提高本地模型使用比例。

12 個月後：擴展到跨系統

把同一套 contract 模式擴到 ERP、Y-CRM、WMS、MES、RFID、EMS，但每個 domain 都保留自己的 source-of-truth、answer templates 與 authz 邊界。

參考來源

外部成熟做法的對應關係

取法

這份設計不是照搬單一供應商，而是把 structured output、grounding、evaluation、risk management 四類成熟做法收斂成 EnClaw 自己的 runtime contract。

OpenAI Structured Outputs：用 JSON Schema 與 evals 讓輸出格式更可控。 Google Cloud Grounding：把模型輸出連到可驗證資料來源，降低幻覺並提供可稽核來源。 Microsoft Foundry Evaluation：用 dataset、agent output 與 traces 做生成式 AI 評估。 NIST AI RMF：以治理、風險管理與可信任 AI 作為企業 AI 落地的基礎 framing。
回到 EnClaw 的差異化

一般平台通常提供模型、grounding 或 eval 工具；EnClaw 要把這些方法產品化成能源管理領域可重播的 answer contract，讓客戶知道同一問題為什麼得到同一答案，以及答案改變時到底是哪個條件改了。
